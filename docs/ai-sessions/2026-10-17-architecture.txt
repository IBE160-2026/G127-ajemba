  Question 3: How should processing keep running when the student leaves the 
  page?

  The PRD (FR-5) says a summary that takes up to 120 seconds must keep going
  after the browser tab closes. A normal Django page request stops when the page
  closes, so the work has to run somewhere else. The page then only starts the
  job and later asks "is it done?" (htmx can check every few seconds). The job
  state ("Processing…", "Ready", "Failed") is saved in the database.

  These are the realistic options:

  How it works
  A. Database-backed task queue with one worker (django-q2 or similar): A
  library
  keeps the job list in the same SQLite database. A second terminal runs a
  worker command.
  B. Heavy queue (Celery + Redis): Needs a separate Redis server.
  C. Hand-made "job" table + a small worker script you run yourself: You write
  the job table and the loop yourself.
  D. Run the work inside the web request: No separate worker.
  ────────────────────────────────────────
  Examiner setup
  A. Database-backed task queue with one worker (django-q2 or similar): Two
  commands, or one script that starts both
  B. Heavy queue (Celery + Redis): Redis install, which is hard on Windows
  C. Hand-made "job" table + a small worker script you run yourself: Two
  commands
  D. Run the work inside the web request: One command
  ────────────────────────────────────────
  Survives page close
  A. Database-backed task queue with one worker (django-q2 or similar): Yes
  B. Heavy queue (Celery + Redis): Yes
  C. Hand-made "job" table + a small worker script you run yourself: Yes
  D. Run the work inside the web request: No. It breaks the PRD.
  ────────────────────────────────────────
  Beginner risk
  A. Database-backed task queue with one worker (django-q2 or similar): Low.
  Documented, and Django's own task system is heading this way.
  B. Heavy queue (Celery + Redis): High. Too many parts.
  C. Hand-made "job" table + a small worker script you run yourself: Medium.
  You'd own all the edge cases, such as crashes and double runs.
  D. Run the work inside the web request: Low, but it fails the requirement.

  I'm not recommending B or D. B is too heavy for "no paid accounts, no
  servers". D breaks FR-5.

● I chose django-q2 with one worker, using the database as the job list. Here is
  why, and what I could and couldn't confirm.

  Why django-q2 and not the Django tasks backend
  - Django tasks backend: Django 6.0 (released 3 December 2025) has a built-in
    tasks system, but it doesn't include a worker for production. You need a
    separate package for that. The package that adds a database worker
    (django-tasks) warned in its older docs that SQLite can run a task twice
    when several workers run. I found no note saying this was fixed. The package
    also says breaking changes can come at any time. That is a risky base for a
    beginner.
  - django-q2: It is a mature library. It can use the database as its job list,
    and the latest release I saw is 1.8.0 (April 2025). It has been around for
    years, so there are many examples for AI assistants to draw on.
  - What I couldn't confirm: The sources disagree on whether django-q2 supports
    Django 6.0. One says "4.2 to 6.0" and another says only up to 5.0. I
    couldn't read the SQLite setup page.
  - Our plan for that: At install time we pin the exact versions and run a small
    test (start the job, close the page, check it finishes). If django-q2
    doesn't work with Django 6, we use Django 5.2, which is still supported.
    I've logged this as a check, not as a settled fact.

  Rules recorded in the architecture
  - Exactly one worker.
  - Every job is safe to run twice. A job first checks whether its result is
    already stored and stops if so. It never charges for the AI call twice.
  - SQLite runs in a mode that tolerates the web app and worker using it at once
    (WAL mode plus a wait timeout). This avoids "database is locked" errors.

  Start script
  There will be one run.py file in the repository, started with python run.py.
  It starts the web app and the worker together, works on Windows, and stops
  both on Ctrl+C. It also works in Demo Mode with no key. A Python script avoids
  the Windows-versus-Mac problems of .bat and .sh files.

  Question 16: How does python manage.py evaluate handle the checks that only 
  you can judge?

  The PRD splits the quality checks into two kinds:
  - Automatic checks the program can do: valid structure, valid slide numbers,
    key terms found in the text, one correct answer per question, and essay
    ranking (good above weak, misunderstanding below good, stable across 3
    runs).
  - Human checks only you can do (§5.4, §5.7): Summary faithfulness (any
    unsupported statement), completeness against your Reference Key Points,
    whether answer keys are right, and whether source references really point to
    the right slides.

  The PRD says "one command writes a report". The question is how the human
  checks fit into that single command and report. Options:

  Matches PRD
  A. Two steps: evaluate runs the AI and the automatic checks, then writes a 
  report with a review sheet (checkboxes) to fill in. evaluate --finish <report>
  reads your sheet and completes the report.: Yes. One
  report, one place, with dates and prompt versions.
  B. Everything automatic only, and you keep your human review in a separate 
  document: Partly.
  The human checks are not tied to the report or the prompt version.
  C. Use a second AI as a judge for the human checks: Violates §5.7. The
  builder's judgement is the stated check. A second AI is not independent
  either.

  My lean is A. Details:
  - Reports live in evaluation/reports/. The file shows automatic results first
    (pass or fail per check), then a review sheet with each Summary and Question
    next to its source slides' text, where you tick items and note findings.
  - evaluate --finish refuses to finish if any box is still unticked, and then
    prints the final pass/fail for the targets in SM-10.
  - evaluate --compare <report1> <report2> shows what changed between two
    reports, for FR-30.
  - The Test Set (lectures, frozen Reference Key Points, frozen Essay questions,
    prepared answers) lives in evaluation/testset/ as plain files and is
    checked by a test that nothing in it was changed after being frozen (a
    stored fingerprint), supporting FR-26.
  - The evaluation never runs inside manage.py test.
